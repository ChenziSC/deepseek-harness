# Agent Note: Local read-only RAG retrieval seam

Status: implemented

English | [中文](2026-09-04-local-rag-retrieval.zh.md)

## Problem

DSH had no provider-neutral way for an agent to retrieve evidence from a developer-supplied knowledge corpus. A learning implementation also needed to compare sparse retrieval, dense retrieval, rank fusion, and neural reranking under one corpus and evaluator without coupling those algorithms to the agent loop or exposing deployment controls to the model.

## Decision

The experimental capability is split into the three complete seam roles. `@deepseek-ai/dsh-experimental-knowledge` defines the provider-neutral `ctx.knowledge` service, branded document and chunk identifiers, ranked hits, and stable caller-visible errors. `@deepseek-ai/dsh-experimental-knowledge-local` provides that service from one immutable local index. `@deepseek-ai/dsh-experimental-tool-knowledge` consumes the service through the read-only `knowledge_search(query)` model tool.

The local provider supports SQLite FTS5 BM25 with deterministic English or mixed Chinese-English analysis, exact float32 Dense scan with fixed-revision BGE-M3, HNSW through USearch, and Reciprocal Rank Fusion over sparse and Dense routes. HNSW queries default to `expansionSearch=1024`; the value remains deployment-configurable and is not model-visible. Request-time automatic routing sends exact identifiers to BM25, cross-script queries to Dense, and ordinary queries to Hybrid, with deterministic fallbacks inside the deployment-configured allowed set. A fixed-revision multilingual BGE cross-encoder can rerank the leading candidates for any retrieval mode; `off` is the performance default, `on` forces reranking for a non-empty result, and `auto` applies it only when the normalized top-two recall-score gap is below the configurable `0.15` default. Recall retains 50 candidates by default while the cross-encoder scores at most the first 20. Every result reports the concrete retrieval and Dense index plus whether reranking actually ran.

Markdown-aware chunking prefers ATX section boundaries, then paragraphs and sentences, and preserves fenced code blocks unless one exceeds the token limit. Section paths join the indexed BM25 and Dense text. After ranking, the provider may attach one preceding and one following same-document chunk without increasing the result count; overlap text is removed and selected neighbors are not repeated. The Consumer bounds matched and adjacent evidence, labels retrieved passages as untrusted, assigns call-local citations, and omits scores and low-level tuning from model context. It encourages one search and permits at most one complementary second search in the same agent turn; validated provider failures consume a slot, while direct non-agent calls are not turn-limited.

Index preparation is an explicit offline operation. Format version 3 streams source documents through bounded transactions into `knowledge.sqlite`, where chunk metadata, section paths, and pre-analyzed SQLite FTS5 input share ordinal keys with optional `dense.f32le` and `dense.usearch` payloads. The manifest records a streaming Latin/CJK corpus profile for routing without retaining another corpus copy. After chunking, the builder records the exact scale and a conservative recommendation based on `vectorCount × dimensions`; an interactive command may confirm Exact-only, HNSW-only, or Both before embedding, while a non-interactive command deterministically accepts the recommendation. HNSW-only still embeds every chunk but does not retain the additional Exact file, and Both is reserved for explicit comparisons. Long-document chunking locates each hard token limit with bounded local probes instead of repeatedly tokenizing the remaining document or its complete prefix. The manifest records the Dense model, vector count, dimensions, scan threshold, recommendation, requested choice, retained payload mode, query default, and HNSW build parameters. Runtime opens SQLite read-only, validates payload types and sizes plus schema metadata, optionally verifies hashes on startup, and exposes a separate command that always recomputes every payload hash. Exact vectors and the HNSW graph load only when requested. SQLite FTS5 owns fixed BM25 scoring parameters; deployment configuration does not expose the first implementation's in-memory `k1` and `b` controls. Plugin startup and search never download corpora or models and never rebuild or modify the index. Dense retrieval and reranking require an explicit populated local model cache; BM25 can run without model weights.

The offline command prepares fixed revisions of BEIR SciFact, MLDR English and Chinese, T2Ranking, and MLQA Retrieval `eng-zho`, builds indexes, verifies their hashes, and evaluates selected BM25, Dense, Hybrid, Exact, HNSW, and `off`/`auto`/`on` reranking combinations under one document-level evaluator. The evaluator folds chunk hits to unique documents and reports Recall, MRR, nDCG, Success, latency, payload sizes, adaptive-reranking application rate, and HNSW recall relative to Exact. Each dataset supports a bounded conclusion: SciFact is an English regression, MLDR covers multilingual long documents, T2Ranking covers Chinese retrieval and scale, and MLQA Retrieval covers Chinese queries over English passages.

Exact/HNSW threshold calibration uses deterministic nested T2Ranking slices containing every selected-query positive followed by official BM25 hard negatives. The largest slice is embedded once; smaller ordinal-prefix indexes rebuild SQLite and HNSW while copying validated Exact vector batches. Derivation rejects a mismatched chunk identity, retrieval text, analyzer, tokenizer, or chunking configuration, so reused vectors cannot silently attach to different content.

## Alternatives considered

**Add retrieval behavior directly to `agent-loop`.** Rejected: retrieval is an optional capability with its own provider and Consumer lifecycle. The existing tool path already lets the model request evidence and keeps the loop independent of corpus and ranking choices.

**Implement the service, local algorithms, and model tool in one package.** Rejected: this would make a future provider depend on local index formats and make a non-model Consumer depend on prompt and rendering policy. The three roles change for different reasons and satisfy the repository's capability-seam structure without adding a provider registry.

**Use a remote vector database or managed search service.** Rejected for this phase: it would add deployment, credentials, network behavior, and provider-specific indexing before the retrieval algorithms can be compared locally. The provider-neutral service leaves that option open without putting remote concerns in the teaching implementation.

**Expose embedding or reranker inference as the product API.** Rejected: callers need ranked evidence, not model tensors. Making model execution the service would leak pooling, dimensions, prompts, and cache layout across the package boundary and would not represent BM25 or Hybrid retrieval.

**Download missing corpora or models at runtime.** Rejected: startup would become network-dependent and mutable, while experiments could silently use changed assets. Explicit preparation and fixed revisions make runtime behavior reproducible and let missing prerequisites fail clearly.

**Keep separate JSONL chunk and JSON BM25 payloads.** Rejected: loading those files materializes the complete corpus and inverted index in JavaScript before a query can run. One embedded SQLite payload supports bounded construction, read-only lookup, schema validation, and BM25 without adding a database service.

## Consequences

Deployments mount one Knowledge provider and may mount the tool Consumer; they do not mount the abstract Service Definition. The provider resolves each request through deployment defaults and allowed sets before retrieval. Index format 3 intentionally supports one read-only corpus, immutable whole-index publication, SQLite FTS5 BM25, Exact Dense scan, and one HNSW implementation. Automatic Dense selection uses the recorded vector-count-by-dimension scan size rather than current-machine detection. The `50,000,000`-element default is a configurable conservative sweet spot, not a measured cross-machine crossover. Requesting an unavailable Dense index fails instead of falling back. Automatic query routing and adaptive reranking are transparent deterministic heuristics, not learned classifiers; callers can override the high-level strategy, while only deployments configure thresholds. USearch graph construction with native automatic threading can produce different graph bytes and approximate neighbors from the same vectors, so each evaluation records the exact index fingerprint. Failed builds may leave an unpublished incomplete directory, and complete benchmark indexes are built, evaluated, and removed sequentially when local storage is constrained. The implementation does not provide incremental updates, multi-corpus routing, access control, remote storage, a second ANN family, inference scheduling, or production recovery.

The checked-in `rag-knowledge` example exercises the assembled BM25 path without external models. Package tests cover the service lifecycle, index validation, Markdown-aware chunking, script profiling, multilingual BM25, Exact-only, HNSW-only and dual-payload Dense retrieval, RRF, automatic routing, adaptive bounded reranking, adjacent expansion, turn-scoped tool limits, cancellation, offline commands, and dataset evaluation. Keyless snapshots exercise the real Loader composition and the model-visible default, lexical, exact, and quality requests. Model-cache smoke tests run in a separate test module without the Transformers.js mocks used by unit tests. Local benchmark results and hardware-specific latency remain experimental evidence rather than product guarantees. SciFact and MLQA Retrieval have full-query local reports; T2Ranking and MLDR use fixed slices. HNSW result overlap is an observation rather than a universal acceptance threshold, and standard qrels metrics own dataset quality conclusions.

Vector reuse is deliberately limited to ordinal prefixes. Arbitrary document subsets would require an identity-mapped vector copier with more metadata and validation, which is not justified by the current calibration experiment.
