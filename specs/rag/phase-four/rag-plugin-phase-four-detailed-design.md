# DSH RAG 插件第四阶段详细设计

## 1. 文档职责

本文将[第四阶段概要设计](rag-plugin-phase-four.md)落实为评测报告、增量向量复用和 Markdown 消融的具体约定。[实施任务](rag-plugin-phase-four-implementation-tasks.md)负责依赖顺序和完成条件。

## 2. 执行顺序

```text
现有格式 3 索引审计
  -> 自动路由评测
  -> 自适应 Reranker 阈值评测
  -> 100 条两轮多跳评测
  -> 两轮触发判断混合评测
  -> 内容寻址向量缓存与现有索引导入
  -> 从零编码执行器优化
  -> 小样本增量与冷启动性能验证
  -> 真实 Markdown 分片消融
  -> 第四阶段验收报告
```

前三项不得等待增量构建完成。Markdown 消融必须位于增量复用之后，以免为两个分片策略重复支付全部 embedding 成本。

## 3. 评测报告扩展

现有聚合 `report.json` 保持简洁，新增 JSONL 明细文件保存每条查询的数据。明细至少包含查询 ID、请求策略、实际召回方式、Dense 索引、Reranker 是否执行、top-2 分差、文档排名、相关文档、单查询指标和耗时。报告不得保存模型内部张量或完整语料正文。

聚合报告记录数据文件摘要、索引指纹、模型 revision、候选数、返回数、阈值、查询数和失败数。部分查询失败时整组运行标记失败，不用剩余查询计算看似完整的平均值。

CLI 为单次评测增加显式 `--adaptive-rerank-min-score-gap-ratio`。阈值扫描由固定配置文件或外层命令依次运行，避免在提供方内加入自动搜索逻辑。

## 4. 自动路由评测

评测器允许请求态模式 `auto`。固定策略运行将 Provider 的允许集合限制为对应单一路径；自动运行允许 BM25、Dense 和 Hybrid，并记录每条查询最终执行的具体策略。

数据分组包括：

1. T2Ranking 普通中文查询，对应 CJK 语料。
2. 使用相同 qrels 的 T2Ranking 跨脚本查询，查询文本经固定翻译得到，证据文档和向量不变。
3. 从索引内容派生并人工核验的 URL、路径、错误码和代码标识符查询。
4. MLDR English 普通英文查询，作为 Latin 同脚本补充样本。

每组同时运行三个固定策略。对每条查询按预先声明的主指标选出离线 oracle，仅用于计算上界和 regret，不作为可部署策略。聚合报告同时给出自动策略相对每个固定策略及相对 oracle 的质量差异。

分类命中率只衡量规则是否选择预期类型；qrels 指标决定该选择是否有实际收益。两者必须分开报告，不能因为路由规则与测试标签一致就声称检索质量提升。

## 5. 自适应 Reranker 评测

每种召回方式先运行 `off` 和 `on`，再根据未重排 top-2 分差分布选择有限阈值。初始候选集合为 `0`、`0.005`、`0.01`、`0.02`、`0.03`、`0.05`、`0.10` 和 `0.15`；连续阈值产生相同触发集合时只保留一个结果。

每个阈值计算：

```text
qualityRetention(metric) =
  (auto(metric) - off(metric)) / (on(metric) - off(metric))
```

当 `on` 没有正收益时，不计算正向保留比例，并将该数据集标记为不适合依据该指标启用 Reranker。MRR@10 和 nDCG@10 分别计算，不合成为一个分数。

阈值只在校准数据上选择，并在至少一个不同数据集上验证。单一阈值不能同时满足各召回方式时，允许保留按召回方式配置的阈值；没有稳定结果时不修改默认配置。

延迟报告保留 p50 和 p95，同时报告触发查询与未触发查询各自的延迟分布。只要触发率超过 5%，整体 p95 进入秒级属于预期结果，不能用低 p50 掩盖。

## 6. 两轮多跳评测

多跳样本采用 JSONL，每条至少包含：

```json
{
  "id": "multi-hop-001",
  "question": "用户问题",
  "firstQuery": "首轮检索词",
  "secondQuery": "补充检索词",
  "firstEvidence": ["document-a"],
  "secondEvidence": ["document-b"],
  "source": "固定语料和标注来源"
}
```

两组证据必须互补，任一组单独存在都不足以完成题目要求。样本生成可以使用模型辅助，但证据 ID、问题含义和两证据需求必须由独立复核者逐条检查；官方 qrels 不能代替正文支持性验证。数据文件记录语料索引指纹、自身摘要和复核结果。

评测包含以下轨道：

- 完整组合问题直接执行一次检索。
- 模型只能生成一条综合查询，工具层限制为一次检索。
- 单轮扩大候选数或返回数，使候选预算与两轮接近。
- Agent 在不被提示必须搜索两次的情况下自主决定是否继续检索。
- 确定性 Oracle 直接执行两条预定义查询，只测量已知子查询能够达到的证据覆盖上限。

完整证据覆盖要求两组必需证据都出现在结果并集中。第二轮边际命中只统计第一轮未出现、第二轮首次出现的必需证据。语义相同或结果高度重复的第二次查询计入重复率。各轨道同时报告实际检索调用数、候选预算、返回数、延迟和 token 成本，避免用更高成本方案与受限基线直接比较。

第一个预定义子查询不能作为正式单轮基线，因为样本要求覆盖两个主题。它与两条预定义查询的差异只验证第二条查询具有构造性互补性，不计为真实 Agent 的产品效果收益。

本阶段不使用通用 LLM-as-judge 判断答案文风或开放式事实正确率。Agent 输出只验证引用的文档 ID 存在、必需证据是否齐全，以及是否遵守两次调用上限。

## 7. 内容寻址向量缓存

向量缓存是构建期产物，不是运行时知识索引。索引命令增加显式缓存目录，并允许从现有 Exact 索引导入：

```text
--vector-cache-dir <directory>
--import-vectors-from <verified-format-3-index>
```

缓存使用 SQLite 或等价的单文件键值存储，避免为每个向量创建小文件。记录至少包含缓存键、float32 向量、维度和创建该向量的编码配置摘要；写入使用事务，只有完整向量批次可见。缓存允许跨索引复用，也让 HNSW-only 发布物保留后续增量构建能力。

向量复用键使用长度明确编码的 Dense 模型配置和完整 Dense 输入文本计算 SHA-256。Dense 输入与运行时一致，由去重后的文档标题、章节路径和原始分片正文组成。配置至少包含模型 ID、revision、模型文件、dtype、pooling、归一化、维度、输入 token 上限和编码实现版本。相同键可以安全复用同一向量；相似但不完全相同的文本不能复用。

源索引导入要求格式 3 和 Exact `dense.f32le`。构建器验证源清单、SQLite、Exact 文件大小和 payload 哈希，逐批读取 Dense 输入和对应向量并写入缓存。任一配置或 ordinal 对齐错误都会终止导入。导入是缓存预热，不修改源索引，也不提供旧格式运行时兼容。

构建流程为：

```text
打开或创建向量缓存
  -> 可选：从已验证 Exact 索引导入缓存
  -> 使用当前分片器生成新 chunk
  -> 按 Dense 输入摘要批量查询缓存
  -> 命中时读取缓存向量
  -> 未命中时按现有批大小调用 embedding
  -> 将完整新向量批次提交到缓存
  -> 按新 ordinal 写入完整新 Exact 向量序列
  -> 从新向量序列构建可选 HNSW
  -> 完成 SQLite、清单和 payload 校验后发布目录
```

缓存查询和写入均使用有界批次，不要求把百万级摘要、文本或向量全部保存在 JavaScript 堆中。目标向量按新 ordinal 顺序组装，因此文档删除、插入或重排不会继承旧 ordinal。

源索引始终只读。目标目录遵守现有“先写载荷、最后发布 manifest”规则；失败不得修改源索引，也不得发布可加载的半成品目标。

首版不复用或局部修改 HNSW 图。文档变化后始终从完整的新向量序列重建 HNSW，避免引入删除标记、图压缩和跨版本更新语义。

## 8. 从零编码执行器

空缓存时，所有 Dense 输入都会进入编码执行器。优化按以下顺序进行，每一步都使用同一抽样语料与当前串行固定批次实现比较：

1. 记录分片、token 统计、模型加载、tokenization、推理、向量写入和 HNSW 构建的独立时间，先确认主瓶颈。
2. 评估“最大文本数加最大 token 总量”的双重上限，检查吞吐、结果一致性和单批内存。
3. 评估有限窗口内按 token 长度分桶，检查 Transformer padding、向量差异、Exact 排名和 qrels 指标；未通过质量门槛时不保留实现。
4. 仅在 I/O 等待达到可观比例时评估有界生产者和消费者队列，不为了形式上的并发增加状态机。
5. 抽样比较不同固定批次、一个和两个模型 worker、ONNX Runtime 线程配置以及独立 HNSW worker。只有重复运行均提高吞吐且没有超过 RSS 上限的方案才成为默认值。

动态批处理和分桶不得改变输入文本、截断上限、pooling 或归一化。批次组成可能导致浮点末位差异，因此结果验证使用向量最大绝对误差、余弦相似度、Exact 排序和 qrels 指标，不要求不同批次策略生成字节完全相同的文件。

每个成功编码批次先原子写入缓存，再进入目标索引组装。进程中断后，重新运行能够命中已经提交的缓存项；未完整提交的批次重新编码。

## 9. 增量与从零构建验证

正确性测试覆盖：

- 完全相同语料，所有向量复用且 embedding 调用为零。
- 修改一篇文档，只重算受分片变化影响的 Dense 输入。
- 新增、删除和重排文档后，新 ordinal 与向量仍一一对应。
- 标题或章节路径变化会使对应 Dense 输入失配并重新编码。
- 模型 revision、维度或输入上限不同会拒绝复用。
- 重复 Dense 输入可复用同一向量。
- 缓存中损坏或维度错误的向量会被拒绝。
- 取消和构建失败不会修改源索引、暴露未提交缓存批次或发布目标 manifest。

性能验证使用约 1,000 至 5,000 个分片的固定样本。冷启动组使用空缓存比较固定批次、动态 token 批次、长度分桶和经过验证的并行配置；增量组对 0%、1%、10% 和 100% 内容变化分别构建。每组至少重复三次，报告 chunks/s、tokens/s、padding 比例、embedding 调用数、编码时间、总墙钟时间、峰值 RSS 和临时磁盘。

缓存复用的向量必须与原缓存值逐字节一致。冷启动优化与固定批次结果的逐向量余弦相似度不得低于预先记录的浮点容差，并且 Exact 检索指标不得下降。HNSW 只比较标准 qrels 和 Top-K 重合度，不要求图文件字节一致。

## 10. Markdown 消融

语料使用固定 Git revision 下的真实 Markdown 文件。文档 ID 由仓库相对路径产生，正文保留标题、段落、代码围栏和列表。查询及 qrels 由人工核验，并标注 `heading`、`section-body`、`code-block`、`cross-chunk` 或 `duplicate-heading` 类型。

消融矩阵为：

| 组 | 分片 | 章节路径入索引 | 相邻扩展 |
| --- | --- | --- | --- |
| A | 固定 token 窗口 | 否 | 否 |
| B | Markdown 结构感知 | 是 | 否 |
| C | Markdown 结构感知 | 是 | 前后各一块 |

A 与 B 比较结构分片整体效果，B 与 C 比较相邻扩展。邻居不计入排名命中，但计入完整证据覆盖、上下文 token 数和重复率。

评测至少报告总体和各查询类型的 Recall@5/10/20、MRR@10、nDCG@10、完整证据覆盖率、重复字符比例、返回 token 数、p50 和 p95。结构收益只在预先标注的结构敏感子集上判断，不能事后挑选获益查询形成结论。

## 11. 验证范围

新增评测解析、报告、向量缓存和编码执行器需要单元测试及逐文件 100% coverage。构建测试使用真实小模型或固定向量后端证明缓存命中、断点续跑、动态批处理和结果一致性。自动路由与两轮 Agent 结果若改变模型可见提示、工具 schema 或会话事件，则更新真实 Loader 快照；纯离线报告字段变化不要求模型快照。

阶段收尾运行相关包定向覆盖率、真实模型小样本、知识快照、`typecheck`、`lint`、`doc-sync`、`hygiene` 和 `git diff --check`。不运行新的全量 100k embedding，也不重复已经完成且与变更无关的大矩阵。
