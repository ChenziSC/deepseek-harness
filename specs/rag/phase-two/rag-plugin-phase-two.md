# DSH RAG 插件第二阶段概要设计规格

本文确认第二阶段的发展方向、能力范围、默认行为和评测对象。第一阶段的既有行为、实现结构与实验结论见[第一阶段概要设计](../phase-one/rag-plugin-phase-one.md)和[第一阶段 E1 实验报告](../phase-one/rag-plugin-phase-one-e1-experiment-report.md)。接口、索引格式和运行流程见[详细设计](rag-plugin-phase-two-detailed-design.md)，交付顺序和完成条件见[实施任务](rag-plugin-phase-two-implementation-tasks.md)，实际完成范围、数据集指标和未通过项见[第二阶段验收报告](rag-plugin-phase-two-acceptance-report.md)。

## 1. 定位

第二阶段将插件定位为本地优先、可评测的轻量 RAG 检索组件。开发者可以把已有中英文文档构建为本地只读索引，agent 通过统一工具检索证据，DSH 现有 agent loop 继续负责工具调用和答案生成。

“轻量”表示单机运行、离线建索引、依赖和操作步骤有限，不表示只能处理小语料。插件可以为大于 Exact 甜点范围的语料构建 HNSW，但不承诺百万级分片一定能在任意开发机上完成，也不承担远程向量数据库、分布式检索和知识库管理平台的职责。

## 2. 目标

第二阶段包含：

- 使用同一个多语言稠密模型处理中文、英文和中英文混合语料。
- 为 BM25 增加适用于中文和中英文混排文本的分析器。
- 保留精确向量检索，并增加 HNSW 近似最近邻索引。
- 默认使用性能模式，并提供显式的质量模式。
- 允许开发者或用户在受控选项内组合 BM25、Dense、Hybrid、精确检索、HNSW 和 Reranker。
- 使用英文、中文、长文档和跨语言数据集分别验证能力。
- 记录检索质量、HNSW 近似损失、查询延迟、索引构建时间、索引体积和峰值内存。
- 保留第一阶段 SciFact 实验的可复现性。

第二阶段不以支持更多检索算法为目标。HNSW 已属于 ANN，用户可见选项只区分 `exact` 和 `hnsw`，不增加含义不明确的 `ann` 模式。

## 3. 非目标

第二阶段不包含：

- IVF、IVF-PQ、DiskANN 或多个 HNSW 实现之间的横向比较。
- 远程或托管向量数据库。
- 分布式索引、分片服务和多机查询。
- 多租户、权限过滤和知识库管理界面。
- 实时增量索引、自动同步和复杂索引迁移。
- 自动训练、微调和参数搜索。
- 由模型直接设置 HNSW、BM25、RRF 或 Reranker 的底层参数。
- 对企业级可用性、容量和服务等级作出承诺。

## 4. 默认检索行为

插件提供性能模式和质量模式。未指定模式时使用性能模式。

| 模式 | 召回方式 | Dense 索引 | Reranker |
| --- | --- | --- | --- |
| 性能模式 | Hybrid | `auto` | 关闭 |
| 质量模式 | Hybrid | `auto` | 开启 |

`auto` 由本地提供方根据分片后的向量扫描量解析：小规模索引使用精确扫描，大规模索引使用 HNSW。自动选择发生在索引构建阶段，不由语言模型根据提示词临时估算，也不在每次查询时重新判断。采用的索引方式必须写入索引清单和评测报告。

自动判断使用以下指标：

```text
scanElements = vectorCount × vectorDimension

scanElements <= exactScanMaxElements  -> exact
scanElements >  exactScanMaxElements  -> hnsw
```

`vectorCount` 是分片后的向量数量，不是原始文件数或文档数；`vectorDimension` 来自实际 embedding 模型。默认 `exactScanMaxElements` 为 `50,000,000`，它是开发者可配置项，但不对用户提示词开放。对于默认的 1024 维 BGE-M3，该值约等于 48,828 个向量，对外可理解为五万分片左右；对于第一阶段的 384 维模型，则约等于 130,208 个向量。

| BGE-M3 分片向量数 | float32 原始向量体积 | `auto` 默认结果 |
| ---: | ---: | --- |
| 6,673 | 约 26 MiB | `exact` |
| 50,000 | 约 195 MiB | `hnsw`，已略超过默认阈值 |
| 100,000 | 约 391 MiB | `hnsw` |
| 200,000 | 约 781 MiB | `hnsw` |
| 500,000 | 约 1.91 GiB | `hnsw` |
| 1,000,000 | 约 3.81 GiB | `hnsw` |
| 2,303,643 | 约 8.79 GiB | `hnsw` |

默认阈值是保守甜点值，不是跨机器的性能分界或质量承诺。它优先避免在约五万条 BGE-M3 分片以上继续默认线性扫描，也避免小索引承担 HNSW 的额外构建时间。接入者可以在构建阶段覆盖该值；评测继续报告 Exact 与 HNSW 的标准 qrels 指标、延迟和结果重合度，但不再要求通过单一数据集寻找普适临界点。

HNSW 主要用于降低查询延迟。构建 HNSW 仍需要为全部分片生成向量，USearch 产物也保存检索所需的向量和图数据；HNSW-only 只是不再额外保留 `dense.f32le`。若产物无法满足本机资源限制，构建应失败并报告估算值，而不是通过切换索引方式掩盖资源不足。

索引构建支持 `auto`、`exact`、`hnsw` 和 `both` 四种产物模式。`auto` 在阈值以下生成 Exact-only，在阈值以上生成 HNSW-only；`exact` 和 `hnsw` 分别只保留一种载荷；`both` 同时保留两份，只用于明确的对照实验。清单记录规模、阈值、推荐值、请求值、最终产物模式和查询默认值。加载阶段只使用实际存在的能力；请求缺失的能力时直接报错。

交互式构建在分片和 SQLite 完成后、embedding 开始前展示文档数、分片数、维度、扫描元素、两种载荷的预计体积和推荐模式。接入者可以接受推荐、改选 Exact、HNSW、Both 或取消；已经显式选择确定模式时不再询问。非交互运行按 `auto` 确定性执行，不因无人确认而阻塞。

选择优先级为：开发者设置的允许范围、开发者显式配置、用户明确请求、自动默认值。用户只能选择开发者允许的组合，不能通过提示词覆盖禁用的模型、索引或资源限制。

## 5. 可选组合

用户可见选择分为三个相互独立的维度：

```text
retrieval: bm25 | dense | hybrid
denseIndex: auto | exact | hnsw
rerank: auto | on | off
```

BM25 不使用 `denseIndex`。Dense 使用选定的向量索引；Hybrid 使用 BM25 和选定的 Dense 索引。Reranker 可以应用于三种召回方式。

提示词只映射到上述选项。例如“只按关键词检索”“使用精确向量检索”“使用混合检索但不要重排”和“质量优先”均可形成明确请求。提示词不能设置 HNSW 图参数、搜索深度、BM25 参数、融合权重、候选数量或模型路径。

未明确指定时，`rerank: auto` 在性能模式中解析为关闭，在质量模式中解析为开启。“质量优先”“开启重排”或同等明确表达可以切换到质量模式；普通知识查询不会隐式启用 Reranker。

## 6. 多语言稠密检索

第二阶段的默认 Dense 模型采用 [BAAI/bge-m3](https://huggingface.co/BAAI/bge-m3)。它使用统一向量空间处理中文、英文和跨语言查询，输出 1024 维向量，并支持最长 8192 token 的输入。插件的本地默认输入长度不直接使用模型上限，长文档仍通过确定性分片控制编码成本。

第一阶段的 `bge-small-en-v1.5` 及其 SciFact 索引继续用于英文回归，不作为第二阶段中英文知识库的默认模型。模型配置必须拥有自己的维度、查询前缀、池化、归一化和输入长度，不能继续把第一阶段的 384 维和英文查询前缀作为全局常量。

BGE-M3 的量化 ONNX 权重约为 568 MB，本机能够加载和执行；主要成本来自百万级语料的离线编码和 1024 维向量索引。以 float32 保存向量时，T2Ranking 的约 230 万条 passage 仅原始向量约占 8.8 GiB，HNSW 图和构建过程还会增加内存与磁盘占用。量化模型权重不会自动量化输出向量。

第二阶段不同时维护另一个多语言模型作为产品默认值。模型效果和资源消耗通过固定数据集报告，不能只引用公开榜单宣布普遍优势。

## 7. 中文与混合文本 BM25

BM25 使用一个确定性的中英文混合分析器：

- 对文本执行 Unicode NFKC 规范化。
- 英文字母和数字按连续词项切分，英文统一为小写。
- 中文字符生成 unigram 和 bigram。
- 中英文、数字和标识符可以出现在同一文档和同一查询中。
- 建索引和查询必须使用完全相同的分析器版本。

该方案不依赖外部分词词典，优先保证本地安装简单、结果稳定，并能够处理技术文档中的 API 名称、代码标识符和中英文混排内容。第二阶段先通过 T2Ranking 验证其质量；只有结果证明字符词项不足时，后续阶段才考虑词典分词。

## 8. 中英文混合知识库

一个索引可以同时包含中文、英文和中英文混排分片，不按语言建立不同的向量空间。多语言 Dense 负责语义和跨语言匹配，BM25 负责同语言词项、数字和共享标识符匹配。

纯中文查询和纯英文文档通常缺乏共同词项，因此跨语言召回主要依赖 Dense。Hybrid 不能把 BM25 的同语言优势解释为跨语言能力，跨语言质量必须由独立数据集验证。

MLDR 和 MIRACL 虽然包含多种语言，但每种语言拥有独立的语料、查询和 qrels；它们不是天然的中英文混合索引。将多个语言分片放入同一索引可以验证共存和路由行为，但不能凭原始 qrels 证明跨语言相关性。

## 9. 重排序

第二阶段继续使用 [BAAI/bge-reranker-v2-m3](https://huggingface.co/BAAI/bge-reranker-v2-m3)。该模型支持多语言，可以处理中文、英文、中英文混排以及查询与文档语言不同的文本对。

Reranker 仍是独立开关，不与 Hybrid 绑定。第一阶段本机实验中，Hybrid 不重排的 p50 为 14.18 ms，Hybrid 加重排的 p50 为 10,478.63 ms，因此普通查询默认不启用重排。质量模式必须单独报告重排带来的指标收益和延迟成本。

召回默认保留 50 条候选，Reranker 默认只处理前 20 条并把未重排的剩余候选接在其后。`rerankerCandidateCount` 是开发者配置，不能由用户提示词设置；该默认值用于限制本机交叉编码成本，不表示所有数据集的质量最优点。

多语言支持不等于跨语言质量已经得到证明。MLQA Retrieval 的 `eng-zho` 配置负责验证中文查询重排英文候选的实际效果；配置名按“语料语言-查询语言”排列。

## 10. 数据集范围

第二阶段只使用以下四组数据，不纳入 MIRACL 和 mMARCO 全量实验。

### 10.1 SciFact

[BEIR SciFact](https://github.com/beir-cellar/beir/wiki/Datasets-available)保留为第一阶段英文回归集，确保模型配置、索引格式和检索策略扩展没有破坏既有行为。它不承担中文和大规模索引验收。

### 10.2 MLDR 中文与英文

[MLDR](https://huggingface.co/datasets/Shitao/MLDR)用于中英文同构评测和长文档实验。中文与英文各包含 200,000 篇文档、10,000 条训练查询、200 条开发查询和 800 条测试查询，并提供开发集和测试集 qrels。

MLDR 查询由模型根据文档内容生成，适合验证语言支持、分片和索引路径，不单独用于证明真实搜索场景中的普遍质量。

### 10.3 T2Ranking

[T2Ranking](https://github.com/THUIR/T2Ranking)是第二阶段中文质量和规模主基准，包含 2,303,643 个中文 passage、258,042 条训练查询、24,832 条开发查询和人工四级相关性标注。数据集提供 BM25、DPR 和 Cross-Encoder 的评测脚本与公开结果。

全量数据用于 HNSW、中文 Hybrid 和 Reranker 的阶段验收，不进入默认 CI。下载时只获取语料、开发查询和 qrels，不获取训练负例和模型文件。

### 10.4 MLQA Retrieval `eng-zho`

[MLQA Retrieval](https://huggingface.co/datasets/mteb/MLQARetrieval)用于跨语言检索验证。第二阶段固定使用 `eng-zho` 配置的测试集，以中文问题检索英文上下文，并使用数据集自带的 corpus、queries 和 qrels 报告 Recall@20 和 Recall@100。

MKQA 只提供多语言问答标注，不提供可直接连接到 BEIR Natural Questions corpus/qrels 的检索标识，因此不作为本阶段检索基准。MLQA Retrieval 验证的是中文查询能否召回英文证据，与把中英文文档放入同一个索引的共存测试不同。两种场景都必须通过，但只以 MLQA Retrieval 结果声明跨语言检索质量。

## 11. 评测分层

第二阶段分别报告三类结果：

| 类别 | 指标 | 目的 |
| --- | --- | --- |
| 标准检索质量 | Recall、MRR、nDCG、Success | 与数据集 qrels 和公开结果比较 |
| HNSW 近似质量 | 相对精确 Dense 的 Recall@k | 测量近似索引造成的结果损失 |
| 本地资源成本 | 向量搜索阶段与完整检索的 p50、p95，构建时间、索引体积、峰值内存 | 观察默认阈值的余量并判断本机和轻量部署是否可接受 |

同一组比较必须固定语料、分片、模型 revision、候选数量、查询集合和评测器。Exact 与 HNSW 使用相同向量，避免把模型差异误认为索引差异。

完整数据集和真实模型评测在本地显式执行，不进入默认 CI。CI 继续使用微型确定性语料覆盖组合解析、中文分析器、HNSW 与精确结果对照、模式覆盖和错误路径。

受本机存储限制，SciFact、MLDR、T2Ranking 和 MLQA Retrieval 的完整索引按实验顺序构建、评测和删除，不同时常驻。每次删除前先保存机器可读指标、构建耗时、峰值内存和各载荷体积；微型 CI 索引与模型缓存不受此轮换规则限制。

## 12. 验收标准

- 默认性能模式解析为 Hybrid、Dense 索引自动选择和关闭 Reranker。
- 明确的质量优先请求开启 Reranker；普通知识查询不会隐式开启。
- 开发者可以限制允许的检索方式、Dense 索引和重排模式，用户请求不能越过该限制。
- `auto` 按 `vectorCount × vectorDimension` 和构建时记录的阈值确定性解析；默认采用 `50,000,000` 个向量元素的保守甜点值，并允许构建时覆盖。
- 交互式构建在 embedding 前展示准确分片规模、预计载荷体积和推荐模式；非交互构建不等待确认。
- Exact-only、HNSW-only 和 Both 三种产物都能被加载，运行时不会为缺失能力临时补建或静默回退。
- 中文、英文和中英文混排文档可以进入同一个索引并完成 BM25、Dense 和 Hybrid 检索。
- SciFact 英文回归、MLDR 中英文、T2Ranking 中文规模评测和 MLQA Retrieval 跨语言评测均能生成机器可读报告。
- HNSW 报告同时包含相对精确 Dense 的召回损失和性能收益。
- 性能模式和质量模式分别报告检索质量与延迟，不把 Reranker 的收益描述为无成本提升。
- 插件保持单机、离线构建和只读索引，不引入第二套 ANN 算法或远程向量数据库。

## 13. 已知风险

- BGE-M3 的模型和 1024 维向量明显大于第一阶段模型，百万级建索引耗时和内存可能成为主要限制。
- T2Ranking 和 MLDR 与 BGE-M3 的训练来源存在关联，其结果适合比较系统路径，但不能单独证明模型对未知领域的泛化能力。
- 中文字符 unigram 和 bigram 会扩大 BM25 索引；若质量或体积不符合预期，需要在后续阶段重新评估分词方案。
- HNSW 的结果是近似的，索引参数和查询参数变化会影响召回率与延迟，报告必须记录最终解析配置。
- 跨语言 Dense 可以召回语义相近的异语言内容，但 BM25 通常不能贡献同等能力，Hybrid 的收益会随查询和语料语言组合变化。
