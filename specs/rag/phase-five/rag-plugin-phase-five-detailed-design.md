# DSH RAG 插件第五阶段详细设计

## 1. 文档职责

本文将[第五阶段概要设计](rag-plugin-phase-five.md)落实为语义分片算法、索引记录、Agent 搜索预算、冲突处理、安全提示和评测协议。[实施任务](rag-plugin-phase-five-implementation-tasks.md)负责依赖顺序和交付条件。

## 2. 执行顺序

```text
冻结第四阶段基线和可复用缓存
  -> 有界多轮搜索配置与提示
  -> 轻量安全提示与证据结果边界
  -> 多预算、冲突处理和安全评测
  -> 语义边界算法小样本验证
  -> 语义分片与边界向量缓存（pilot 通过时）
  -> 三种分片正式消融和默认值决策
  -> 候选默认分片与搜索预算组合回归
  -> 第五阶段验收报告
```

有界搜索是冲突处理的前置能力。轻量安全提示和工具结果边界在有界搜索实现稳定后、真实 Agent 评测前完成，使多预算、冲突和攻击评测使用同一份最终模型可见文本，避免重复运行高成本评测。

语义分片与在线搜索循环没有实现依赖，但完整实现和三路建库成本较高且收益不确定，因此排在低成本 Agent 改造及评测之后。智能体化 RAG 先使用第四阶段固定的 Markdown 默认索引隔离搜索策略变量；语义分片成为候选默认值时，只运行候选分片与候选搜索预算的组合回归，发现交互回退后才扩大评测矩阵。

## 3. 语义分片算法

### 3.1 策略与接口

`ChunkingStrategy` 增加 `semantic-boundary-v1`。现有同步 Token 与 Markdown 分片路径保持不加载模型；索引构建器只在该策略下调用异步语义分片器。公共 `Knowledge` 搜索 API不增加分片字段，运行时从不可变索引读取已完成的分片。

语义分片配置至少包含语义模型 ID、完整 revision、模型文件、dtype、维度、模型输入上限、上下文窗口单元数和最小分片 token。全部字段进入索引清单和缓存身份。新增字段使索引清单无法继续由格式 3 完整表达时，索引格式一次性升级，SQLite 表结构不因仅增加构建元数据而变化；旧格式不进入运行时兼容路径。

### 3.2 候选单元

候选单元按原文顺序产生：空行分隔的段落优先，段落超长时使用中英文句末边界，句子仍超长时使用 tokenizer 硬切分。完整且未超过 `maxTokens` 的 Markdown 代码围栏作为一个单元，避免仅为计算语义距离破坏代码。Markdown 标题用于记录 `sectionPath`，但不被强制选为语义切点。

空白裁剪、Unicode code point 安全、确定性文档排序和 token overlap 沿用现有分片器。单元文本和最终分片正文必须是原文切片，不允许语义模型改写内容。

### 3.3 边界评分

每个候选单元使用有限上下文窗口形成边界输入。默认窗口包含当前单元及前后各一个单元；文档边缘只使用存在的单元。所有输入使用同一语义模型批量编码并进行 L2 归一化，相邻窗口的边界距离为：

```text
distance(i, i + 1) = 1 - cosine(embedding(i), embedding(i + 1))
```

从当前分片起点开始，只考虑能使分片长度位于 `[semanticMinTokens, maxTokens]` 的候选边界，并选择距离最大的一个；距离相同时选择更靠后的边界，以减少不必要的小分片。没有满足最小长度的候选边界时选择不超过 `maxTokens` 的最后一个安全边界；没有安全边界时回退到现有硬 token 切分。

该算法不使用按文档计算的百分位阈值。百分位方案会强迫语义一致的长文档按固定比例产生断点，也使不同长度文档的阈值难以比较；固定绝对阈值又高度依赖模型和语料。`semantic-boundary-v1` 使用“受 token 区间约束的最大语义间隙”，让分片数量主要由同一长度预算决定，语义距离只决定切点。

### 3.4 缓存与构建阶段

现有内容寻址向量缓存扩展为带用途版本的向量记录。最终检索向量使用现有用途；语义边界向量使用 `semantic-boundary-v1` 用途，并把模型配置、算法版本和准确窗口文本纳入 SHA-256 输入。两个用途即使文本相同也不得互相命中。

构建阶段分别计时：

```text
语料暂存
  -> 候选单元解析与 token 计数
  -> 语义边界缓存查询
  -> 缺失边界向量编码
  -> 最终分片组装
  -> 最终 Dense 缓存查询与编码
  -> SQLite、Exact 和可选 HNSW 组装
  -> manifest 发布
```

语义边界向量按成功批次提交缓存。失败或取消不得发布目标 manifest。局部修改只允许使同一文档内正文变化涉及的单元窗口失效；其他文档的边界缓存必须保持命中。最终分片边界变化仍可能使该文档多个最终 Dense 输入失效，这是算法成本而不是缓存错误。

语义分片不能复用边界向量作为最终检索向量。前者编码局部单元窗口并服务于切点选择，后者编码标题、章节路径和完整最终分片，输入与用途不同。

## 4. 三路分片评测

### 4.1 输入

固定输入至少包含：

- 第四阶段20个真实 Markdown 文件和25条已核验查询。
- 扩充后的真实 Markdown 查询，使标题、章节正文、代码围栏、跨块证据和重复标题每类不少于15条。
- 长段落、弱标题或无标题长文档轨道，优先复用已有 MLDR 原始语料和 qrels。
- 一个短文档回归轨道，确认额外分片算法不会因样本过短产生虚假收益。

每份语料记录来源 revision、文件摘要、模型 revision、分片参数和查询摘要。人工证据标注需要指出必需短语或证据范围，只有文档级 qrels 的轨道只用于标准排序指标，不用于单命中完整率。

### 4.2 矩阵

三个分片策略使用相同 `maxTokens` 和 `overlapTokens`，分别构建 BM25 加 Dense 索引。主矩阵固定 Exact Dense、Reranker `off`、`adjacentChunkCount=0`、相同候选数和返回数，并运行 BM25、Dense、Hybrid。

语义算法参数只允许在独立 pilot 集上选择一次，正式集合不得继续调参。正式报告同时给出总体、语料轨道、查询类型和召回方式结果，不允许只依据汇总平均值掩盖单一路径回退。

### 4.3 默认决策

先应用概要设计中的质量与成本门槛，再按以下顺序决策：

1. 存在唯一通过者时选择该策略。
2. 多个策略通过时，优先选择完整证据覆盖率更高者；差异低于1个百分点时选择返回 token 更少者；仍相同时选择冷构建成本更低者。
3. 没有策略通过时保持当前 `markdown-structure-v1`，不把测试集最优者直接设为默认。

默认值决策只针对单索引方案。为 BM25 与 Dense 维护不同分片索引需要双倍索引路由、存储和生命周期管理，不在本阶段顺带实现。

## 5. 有界搜索循环

### 5.1 运行时预算

`tool-knowledge` 的 `maxSearchesPerTurn` 从当前最大值2扩展为1至8的部署配置。主评测使用最大值8执行一次自然搜索轨迹，并在第1、2、4、6、8次成功调用后保存检查点；每个检查点从同一前缀结果计算累计覆盖、调用成本和边际收益，不重新调用检索器或模型。候选默认值由这些检查点选择，不在实现前预设为4或6。

新增 `turnOutputMaxChars`，限制一个 Agent turn 中所有成功搜索结果的累计渲染字符数。每次调用先预留调用编号和引用编号区间，再根据剩余累计预算裁剪结果；失败、超时和重复查询仍消耗调用次数，但不消耗成功结果字符预算。预算耗尽时返回稳定错误，Agent必须使用已有证据回答并说明缺口。

提示要求 Agent 每次只发出一个搜索调用并检查结果后再决定下一步。依赖证据中的不透明标识符时，后续查询只包含该标识符，避免通用词使后续档案提前进入结果。工具按 NFKC、转为小写、首尾裁剪和连续空白折叠规范化查询。同一 turn 内完全相同的规范化查询被拒绝，防止无进展循环；不使用 Dense 模型比较查询语义，也不拒绝针对同一实体但新增限制条件的有效查询。

检查点只证明“同一搜索策略继续执行时，第 N 次调用累计获得了多少证据”，不能完全替代真实硬上限运行。Agent在知道或触发预算耗尽后可能改变停止和回答行为，因此现有上限2与根据检查点选出的候选默认值各执行一次端到端验证；其他中间预算不重复完整Agent运行。评测器可以按索引指纹、查询和请求策略缓存确定性检索结果，但不能把不同Agent生成的查询视为同一次调用。

### 5.2 模型提示

稳定提示要求 Agent：

- 在首轮前识别独立证据需求，但不输出隐藏推理过程。
- 首条查询覆盖同一主题可以共同召回的字段。
- 每轮后只针对仍无直接支持的需求、冲突或中间事实继续搜索。
- 查询包含上一轮得到的不透明标识符时，优先直接使用该标识符。
- 不用改写同一查询的方式机械增加结果数量。
- 证据已经充分或无法提出具体新查询时停止。
- 达到预算后基于现有证据回答并明确仍未确认的事项。

Knowledge 提供方仍执行一次独立搜索，不维护 Agent 的搜索计划。调用次数、累计输出和重复查询由工具 Consumer 管理，不修改 `agent-loop`。

### 5.3 引用

引用编号继续按每次调用的 `maxResults` 预留不重叠区间，因此提高搜索上限不会改变同一 turn 内的唯一性。工具结果被裁剪、失败或重复查询拒绝时，已预留区间不重新分配。最终回答中的每个 `K<n>` 必须能映射到本 turn 的一条实际返回证据。

## 6. 冲突处理

冲突评测为每条样本记录冲突命题、冲突文档、可选裁定文档和期望状态：`resolved` 或 `unresolved`。裁定文档必须直接提供能够区分冲突的时间、对象、适用范围、版本或权威决定，不允许把“排名更高”标成裁定理由。

Agent 的正确行为为：

1. 首轮出现实质冲突时不立即选择一方。
2. 构造针对缺少判别信息的查询。
3. 找到裁定证据时引用冲突双方及裁定依据，并说明适用条件。
4. 找不到裁定证据时保留冲突，指出需要用户或外部权威确认的事项。

本阶段不向 `KnowledgeHit` 增加通用时间、有效期或权威等级字段。不同知识域无法共享可靠的权威排序规则；相关信息作为正文和来源由 Agent读取，后续若引入结构化知识治理再设计提供方无关字段。

## 7. 轻量安全边界

### 7.1 威胁范围

本阶段假设索引正文可能包含恶意自然语言指令、伪造角色标签、工具调用建议、外部地址、秘密读取要求或伪造引用。攻击者不能直接修改系统提示、工具 schema、索引清单或本机模型文件；这些属于部署和索引完整性问题，继续由现有校验和文件权限负责。

### 7.2 防护

系统提示和每次工具结果都明确标识证据不可信。工具结果保持结构化字段，并在正文前使用稳定说明，声明正文只能支持事实判断，不能授权操作或覆盖上层指令。正文不执行、不抓取、不解析为工具调用，也不因出现类似 `K1`、`system` 或 JSON 的文字而改变引用分配。

安全规则不尝试删除或改写正文中的疑似攻击文本，因为简单过滤可能破坏需要分析的安全文档和代码示例。模型是否执行有副作用的工具继续受对应工具权限和用户授权约束；RAG 插件不增加一套平行授权系统。

### 7.3 验证

单元测试验证不可信提示和引用边界被稳定渲染，任意证据正文不能改变结构化 `citation` 字段。无密钥快照覆盖模型可见的提示和结果。真实 Agent 小样本至少包含六类攻击，并记录是否服从恶意指令、是否产生非必要副作用工具调用、是否泄露测试秘密、是否采用伪造引用以及是否仍能回答正文中的正常事实问题。

安全验收不以“模型没有输出攻击文本”为标准；模型可以引用或讨论恶意文本，但不得把它当成需要执行的指令。报告必须说明提示级防护不能提供确定性注入免疫。

## 8. 评测报告

机器可读报告分为三组：分片消融、搜索预算与冲突处理、安全攻击样本。每组记录输入摘要、代码 revision、模型 revision、配置、失败数和逐样本明细。搜索预算报告保存完整调用序列，并为第1、2、4、6、8次调用生成前缀投影；提前停止的轨迹在后续检查点保持相同证据和调用数，不虚构额外搜索。与硬件相关的时间和 RSS 单独标记，不作为跨机器保证。

模型评测保存最终输出、工具调用参数、实际策略、引用映射和可观察的停止原因，不保存隐藏推理。模型调用失败、工具超时或预算拒绝必须作为失败记录保留，不能从平均值中静默删除。

## 9. 验证范围

语义分片、缓存用途隔离、累计预算、重复查询、引用编号和安全结果边界需要单元测试及逐文件100%覆盖率。提示或模型可见工具输出变化更新真实 Loader 快照。语义模型使用本地固定 revision 小样本烟测；正式消融只运行固定规模，不扩大到全量100k语料。

阶段收尾运行相关包定向覆盖率、知识快照、`typecheck`、`lint`、`doc-sync`、`hygiene` 和 `git diff --check`。不重复第四阶段中与本阶段无关的 Reranker 阈值或 Exact/HNSW 大规模矩阵。
